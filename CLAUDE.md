# whenever

Finn tid (nb) / Whenever (en): find the day or time that suits most people,
at finn-tid.apphub.casa and whenever.apphub.casa. In nb, nn, sv, da, is and
en. The host picks the default language (`finn-tid.` → nb, `whenever.` →
en, anything else → the browser's first Nordic language, else en).

## Layout

TypeScript (strict), no framework, no runtime dependencies, no third-party
requests. Imports use `.ts` extensions; TS-only syntax that needs
transforming (enums, namespaces, parameter properties) is off
(`erasableSyntaxOnly`), so Node runs the tests straight from the sources.

- `src/shared/model.ts`: pure and shared by the app and the Worker, and the
  home of the data types (`PollEvent`, `View`, `Person`, `Tally`, ...).
  Dates (UTC `YYYY-MM-DD` strings, weekday 0 = Monday), holidays,
  selection helpers, option keys, `sanitizeEvent`/`sanitizeEntry`,
  permissions (`canAdd`/`canEdit`), results (`tally`, `bestOptions`,
  `windows`, `bestWindows`), `LIMITS`, retention.
- `src/app/`: the frontend, bundled by esbuild into one file.
  - `app.ts`: UI, routing, the event form, overview/results, the answer
    editor. `i18n.ts`: strings (nb and en) and date formatting; `lang/`
    the other languages' strings. `api.ts`: fetch wrapper.
    `store.ts`: localStorage. `ui.ts`: `$`, `esc`, dialogs, toast, QR.
  - `calendar.ts`: month grids (`calendarHtml`) and drag/tap painting
    (`bindPaint`). `timegrid.ts`: the drag-to-paint time grid (`TimeGrid`).
  - `theme.ts`: the colour theme; `theme-head.ts` is its entry for the
    small classic script in `<head>` (see Themes below).
  - `styles.css`: the one stylesheet.
  - `vendor/qrcodegen.js`: Nayuki's MIT QR library, copied from scorepad,
    with types in `qrcodegen.d.ts`. Don't edit by hand.
- `src/worker/index.ts`: `/api/*` only (`run_worker_first`): routing, JSON
  parsing, rate limit, turning the Bearer token into a credential.
  `poll.ts`: the `Poll` Durable Object, which decides everything about who
  may do what. `link.ts`: making and parsing link tokens. `lookup.ts`: the
  `Lookup` Durable Object (the email index and its codes), `codes.ts` the
  limits on codes (pure), `mail.ts` the code mail and a small SMTP client.
- `public/`: static files copied as they are: `index.html`, `privacy.html`,
  `_headers`, fonts, icons.
- `scripts/build.mjs` writes `dist/` (what the Worker serves): `public/`
  plus `app-<hash>.js`, `styles-<hash>.css` and `theme-<hash>.js` (an
  iife, built separately), minified with sourcemaps. The pages refer to
  `/app.js`, `/styles.css` and `/theme.js`, which the build rewrites to the
  hashed names; `_headers` makes those immutable. The hashes are
  why a deploy never mixes new HTML with cached old code (the apphub.casa
  zone caches CSS/JS for 4 hours). wrangler bundles the Worker itself.
- One `tsconfig.json` per directory (DOM types only in `src/app`, Worker
  types only in `src/worker`, Node types only in `test`), all extending
  `tsconfig.base.json`. `worker-configuration.d.ts` is generated by
  `wrangler types` (part of `npm run check`) and not committed; run it
  again after changing `wrangler.jsonc`.

## How it works

- **One Durable Object per event** (`idFromName(eventId)`), SQLite tables
  `meta(k, v)` and `people(...)`. `exists()` never creates tables, so probing
  a wrong id leaves no storage; only `POST /api/events` creates. An alarm
  deletes everything at `max(last date + 31 days, now + 7 days)`
  (`expiresAt`, `deleteAt`); `RETENTION_DAYS` is what the UI and privacy page
  say.
- **Links are random secrets stored with the event.** `/e/<eventId>` is
  the public event link; `/e/<eventId>/<token>` is an admin or personal
  link. The token (`src/worker/link.ts`, patterns `TOKEN`/`TOKEN_RE` in
  `model.ts`) is a 16-hex selector (the participant id, or the event's
  `adminId`) followed by a 22-char random secret (128 bits): 38 chars, no
  separator. The Poll object finds the row by selector and compares the
  secret in constant time (`same()`); it also makes every token. Resetting
  a link stores a new secret, and the old one reads as `link: 'invalid'`.
  Secrets are stored unhashed on purpose, so the admin can copy a
  participant's current link again. Links need no Worker secret or key. Never
  put tokens in query strings or logs; the client sends them as
  `Authorization: Bearer`.
- **Option keys:** dates mode `YYYY-MM-DD`, times mode `YYYY-MM-DDTHH:MM`
  (wall-clock in the event's `tz`; nothing converts time zones). An event's
  `options` is the allowed set; answers map key → 1 (yes) or 2 (maybe), and
  `cleanAnswers` drops keys that aren't options. Editing an event prunes
  answers to removed options (the form warns first).
- **Picking days: there is no date range in the form.** The organiser
  picks days in a calendar that shows from today to `Draft.until` (at
  least six weeks ahead, to a month's end; "Show next month" adds one, up
  to `MAX_MONTHS`). Past days can only be unpicked (when editing). The
  event's `start`/`end` are just its first and last offered day, filled in
  by `draftToEvent`; the server still checks them and the limits.
- **Selection helpers only change the selection.** Period buttons (next 2
  weeks, next 4 weeks, all of next month) replace the selection with those
  days. Weekday/group chips (Hverdager, Helger, Helligdager, Ma…Sø, week
  numbers) act on the days shown from today: if any of theirs are picked
  they drop them, otherwise they pick them all (`selectGroup`), so "next 4
  weeks" then "Helger" drops the weekends. They show a tri-state
  (`weekdayState`, `groupState`). The stored event is just the explicit
  set, so a single Saturday can always be picked by hand. Keep it that way:
  never store a "no weekends" rule.
- **Holidays:** each event has a calendar, `holidays`: `no`, `se`, `dk` or
  `none` (`HOLIDAY_CALENDARS`), picked under Innstillinger. Events stored
  before it existed have none, so read it with `holidayCal()` (Norway);
  `sanitizeEvent` fills it in. A new event guesses from the browser's time
  zone, then its languages, else `none` (`guessHolidays`). `holidays(year,
  cal)` gives date → keys: the days off by law plus julaften and
  nyttårsaften everywhere (and midsommarafton in Sweden), since people
  plan around them; no Danish grundlovsdag (not a day off by law) and no
  store bededag after 2023 (abolished). Easter is the Gregorian computus;
  Sweden's midsummer and All Saints are the Saturday from 20 June / 31
  October. Two holidays can share a date (17 May is sometimes Whitsun or
  Whit Monday), so it's a list, and `holidayNames` joins the names. Every
  key needs a `holiday.<key>` string in both languages (tested). They only
  mark the form's calendar and drive the Helligdager chip, which is left out
  with `none`.
- **Ranking:** by default most yes first; on a tie more maybes come
  first, then the earliest. With the `maybeCounts` setting (only offered with
  `maybe`): most yes + maybe first, then most yes. `score` is the number
  shown everywhere (calendar days, list, table sum, best list, the
  "Avtalt" card), so with the default a maybe-only day shows no count.
  `compareScore`, `sameScore` and `ranks` live in `model.ts`. The same
  score is a draw and shares a rank (1, 1, 3): the tiebreak only orders
  inside a draw, since "2 av 3 kan" twice must not look like a win. Every
  option tied for first is green and ringed, and the best list (3 items)
  gets a "Vis N til" button (`bestOpen`) for any first-place ties it leaves
  out, never a bare "+ N". `heat` shades by the score, nudged by the tiebreak by
  less than one person, so on the dates calendar a darker day never ranks
  lower (in the times grid the shading is per slot and the ranking per
  window). Times mode ranks windows of `duration` built from consecutive
  slots, and the top windows don't overlap.
- **Picking the final date:** the admin picks an option (dates) or a
  window start (times) in the detail panel; it's stored as the event's
  `decided`. `sanitizeEvent` drops it unless it is in `decisionKeys`, so
  editing the options away clears it. Picking also closes the event;
  undoing the pick leaves it closed. `decision()` gives the picked tally or
  window for the "Avtalt" card. The picked option is marked everywhere in
  its own colour (`--pick`, one per theme), apart from the "most can" ring
  and the selection: a check badge (`.dk`) on the calendar day and table
  column, a "Valgt" tag in the best list and list rows, a frame around the
  window in the time grid, and a legend entry. "Legg i kalender" builds the `.ics` in the
  browser (`src/app/ics.ts`). Times are wall-clock in the event's `tz`, and
  `zonedUtc` converts them to UTC with `Intl`. The file may only carry the
  public event URL, never a link token.
- **Permissions:** the admin can do everything; `closed` blocks everyone
  else; people edit their own entry; `openEdit` lets anyone edit/delete any
  entry (not with `hidden`, where only the admin sees others' answers).
  Emails are only returned to their owner (and `adminEmail` to the admin).
- **The admin's own answer:** meta `adminPid` is the admin's own entry, so
  with the admin link they are also that participant (`me` in their view):
  they see and set its email, and it's marked "deg". They add it with
  "Legg til dine svar" (`own: true` on the POST); "Legg til svar for en
  annen" (`#answer=new`) makes an entry with no email and shows its link.
  Events from before (or a wrong pick) are fixed with
  `PUT /api/events/:id/own` (`markOwn`, from the role card or the admin
  menu); the entry this device added is only offered as a suggestion,
  never taken for theirs. Deleting it clears `adminPid`. An email the admin
  types on their own entry becomes `adminEmail` while that is empty, so a
  code for it brings both links back; never take it from an email already
  on the entry (`setOwn`), since the entry's personal link can set that,
  and a personal link must never lead to the admin link.
- **Email codes (`/find`):** an address entered on events gets a 6-digit
  code by email, and the code adds those events' links to the device. The
  mail (multipart text + HTML, inline styles, no remote images) also has a
  one-tap link, `https://<host>/find#t=<token>`, to the site the code was
  asked on (`linkHost`; localStorage is per site). The page takes the token
  out of the address bar at once and only redeems it on a tap
  (`POST /api/lookup/link`), never by itself: mail scanners open links. The
  token is 32 base64url characters (`codes.ts`); the `Lookup` keeps its HMAC
  and the address AES-GCM encrypted under a key derived from the token
  (`links` table), since the events need the address. Code and link live
  10 minutes, the link works once, and using either ends both (`used()`).
  - The `Lookup` object (one for the app, `getByName('lookup')`) stores HMACs of
    addresses and IPs under a key it made itself and keeps in its own SQLite.
    It holds `entries` (address → event, until the event's deletion),
    `codes` (10 min, 5 tries) and `asks`.
  - Each `Poll` calls `reindex()` after any write that touches an email.
    The call comes after its own SQL, and it replaces that event's addresses,
    expiring at its alarm time. If it fails, meta `indexed` stays unset and
    `get()` tries again; that is also how events made before this got
    indexed. `destroy` and `alarm` clear the event's entries.
  - Using a code asks each event for `linksFor(email)`, which compares the
    stored addresses, so a stale index entry brings nothing.
  - Limits are in `codes.ts`:
    - per address: 1 a minute, 3 an hour, 6 a day;
    - per IP: 20 a day, plus the `MAIL_LIMIT` binding at 5 a minute;
    - for the app: `MAIL_DAILY_MAX` a day.

    Every ask counts whether or not the address is known; the reply is the
    same (`{ ok }` or 429 `wait.*`); and only known addresses get a code.
  - The mail is sent by `deliver()` in `ctx.waitUntil` after the reply,
    over SMTP to `smtp.forwardemail.net:465` as `SMTP_USER` (also the From
    address). Failures go to Workers Logs as `smtp <step>: <code> <reply>`
    with addresses removed; never log an address or a code.
  - In dev (`npm run dev` sets `--var MAIL_ECHO:1`), a request from this
    machine (loopback `cf-connecting-ip`) gets the code back as `echo`
    instead of a mail, and `x-dev-ip` stands in for its IP.
    wrangler dev rewrites the URL and `Host` to the route's host, so a
    hostname check can't tell dev from production.
- **Routes:** paths `/`, `/new`, `/find`, `/e/:id`, `/e/:id/:token` (SPA fallback
  serves `index.html`), plus hash sub-views `#answer`, `#answer=<pid>`,
  `#edit`. Clicks go through `data-act` delegation to the `actions` map.
  The overview polls every 30 s and on tab focus, only while it's the
  visible view and no dialog is open (`refreshIfIdle`).
- **Painting:** `TimeGrid` paints a rectangle (the first cell decides
  paint or erase). A mouse paints at once. A finger scrolls the page as
  usual (`touch-action: manipulation`): a tap toggles one cell, and holding
  a cell for `HOLD_MS` starts the rectangle, after which `touchmove` is
  cancelled so the page stays put. Never go back to `touch-action: none`:
  the grid covers most of a phone screen and the page couldn't be scrolled.
  The cell under the pointer comes from the grid geometry (`track()`), not
  `elementFromPoint`, and dragging near the window edge auto-scrolls. The
  smoke test's synthetic events can't scroll, so after touching this, check
  real touch over CDP (`Input.dispatchTouchEvent`): a swipe scrolls and
  paints nothing, hold-and-drag paints and doesn't scroll, a tap toggles.
  The calendars (`bindPaint`, form and answers) pick date ranges: a drag
  gives every day from the first to the one under the pointer, in date
  order, the first day's new value, previewed live; days the drag leaves
  get their old value back (`get`). Shift-click or Shift+Enter fills from
  the last day clicked. A finger holds a day for `HOLD_MS` first, like the
  time grid, so swipes scroll and taps toggle; check it over CDP the same
  way. The day under the pointer comes from `elementFromPoint`. Calendar
  days are buttons; the time grid takes arrow keys + Space.
- **Time grid pages** are ISO weeks (`weekPages`), two side by side when
  the grid is at least `WIDE` px, picked with week buttons (a dot = something
  marked there). The day names are sticky; in paint mode they open the
  whole-day menu. The event form warns when participants would page
  through more than three weeks.
- **Undo and redo in the picker** (`history.ts`, pure and tested): the
  draft's `hist` keeps snapshots of `dates`, `times` and `pattern` (sorted
  copies, never the live Sets). Every change to them ends with `commit()`:
  a calendar stroke in `bindPaint`'s `done`, a time-grid stroke in
  `onPaint`, the chips, periods, "Ingen", presets and the day menu. A
  change that touches them without a `commit()` merges into the next step.
  Switching mode or the day's hours resets the history (both rework the
  times). Undo/Redo buttons sit by the count line and the presets;
  Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl+Y work outside the form's fields.
  "Ingen", a period, clearing times and removing a day show a toast with
  an Undo button (`toast(msg, action)`). The history goes with the draft
  (save, cancel, leaving) and survives a language switch.
- **New-event defaults:** nothing picked. In times mode a picked day gets
  9 to 17 (`Draft.pattern`; the presets and "copy to all days" change it).
  Switching mode keeps the picked days.
- **Unsaved changes:** `Draft.dirty` / `AnswerDraft.dirty`. In-app links,
  Back and Cancel ask (`leaveOk`), closing the tab triggers
  `beforeunload`, and the browser's back button keeps the form in memory
  (`app.kept`) until its page is opened again. Clear `dirty` before
  navigating after a successful save.
- **Themes:** Automatisk (default), Lys, Mørk, Hacker, from the theme
  menu in the header (see Header menus). The choice is `theme` in the `whenever-v1` store; `theme.ts`
  puts light, dark or hacker on `<html data-theme>` and the CSS reads only
  that (one variable block per theme, never `prefers-color-scheme`; auto
  resolves through `matchMedia` and follows changes). It runs from
  `theme-<hash>.js` in `<head>` of every page, before anything paints: the
  CSP allows no inline script, and a module would run after first paint.
  Switching only changes the attribute (no render), so a form keeps its
  contents. Hacker uses VT323 (self-hosted, OFL; only fetched there),
  square corners and scan lines; yes stays green and maybe amber, so they
  never blur. New colours go in every theme block.
- **i18n:** nb is the source (its object defines `Key`); en is next to it
  in `i18n.ts`, and nn, sv, da and is are in `src/app/lang/`, each typed
  `Record<Key, Text>`, so a missing or extra key doesn't compile. All are
  bundled (a lazy chunk could be gone after a deploy while an old tab still
  wants it). Plurals are `{ one, other }`, picked by `PLURAL_ONE`:
  Icelandic's "one" also covers 21, 31, ..., so its `one` strings say `{n}`.
  Tests check the keys, that translations keep nb's placeholders, that
  literal `t('…')` keys exist and that every API error code has an `err.*`
  string. Chromium has no Intl data for nn and is (it formats them as
  another language), so their dates come from `OWN_NAMES`, tested against
  Node's ICU. `WEEKDAYS`, `UNITS`, `AND` and `shortDate` are per language
  too: a new language needs an entry in each. Templates mustn't build words
  across languages (`weekdayHint` adds a plural ending to `{day}` in the
  Scandinavian ones; Icelandic says it differently). The header's language
  button shows the language code. User text always goes through `esc()`.
  The privacy page is nb + en only.
- **Header menus:** the events, theme and language buttons (`menuButton`)
  open popover menus (`.dropdown`, `#events-menu` / `#theme-menu` /
  `#lang-menu`, items from `dropItems`). The browser closes them on Esc or a
  click outside and focuses the current choice (`autofocus`); a
  `beforetoggle` handler puts each under its button, and the arrow keys move
  between the choices. The events menu (`eventItems`) is there once this
  device remembers an event: the latest `EVENTS_SHOWN` (8) as in-app links
  (admin link, else personal), then "Show all" to the home page; leaving a
  half-filled form asks first, like any in-app link. Picking a language
  renders again; picking a theme only redraws the theme menu's items
  (`setTheme`), so a form keeps its contents. Browsers without
  popovers (Safari 16, Firefox 124) get the dialog `menu()` instead
  (`canPopover`). Never put `data-act` on a popover's button: the click
  delegation's `preventDefault()` stops it opening. The 30 s refresh waits
  while a menu is open.
- **CSS names:** `.page` is the container and `.bar` the header; the result
  meter is `.meter`. Don't reuse `.bar`/`.wrap`-style generic names (both
  collided once).
- **Privacy page:** `public/privacy.html`, static, nb + en. Keep it true
  when adding storage or a request: no cookies, analytics or third-party
  requests from the browser (the code mails go through Forward Email, and
  the page says so). localStorage keys start with `whenever-`.
- **Security headers:** `public/_headers` sets a strict same-origin CSP
  (no inline scripts) and `Referrer-Policy: no-referrer` (links carry
  tokens). The Worker sets `no-store`, `nosniff` and `no-referrer` on API
  responses and only accepts `application/json` bodies (415 otherwise).

## Testing

- `npm run check`: `wrangler types`, then `tsc` for each directory. Must be
  clean; esbuild and wrangler don't type-check.
- `npm test`: model, link tokens, i18n, the picker's undo history, the code limits and the SMTP client
  against a scripted server (node:test, Node 22.18+ for type stripping; CI
  uses 26).
- `npm run dev` (wrangler dev, which runs the build and rebuilds on
  changes), then `BASE=http://127.0.0.1:8787 npm run smoke`: a browser
  end-to-end check (dates and times events, chips, drag and touch painting,
  undo and redo in the picker, several participants, permissions, link reset, picking the date and the
  `.ics` download, ties and the ranking setting, holiday calendars, the
  events menu, finding events by an email code, the language menu and
  nn/is dates, themes against a dark and a light device). The email-code
  part needs `MAIL_ECHO` (as `npm run dev` sets; with plain `wrangler dev`
  add `--var MAIL_ECHO:1`). It uses `playwright-core`, which has
  no browser: set `PWCHROME` to a Chromium or
  `chrome-headless-shell` binary, e.g. under `~/.cache/ms-playwright/`.
  Screenshots go to `$SHOTS` (default `/tmp/whenever-shots`).
- CI (`.github/workflows/ci.yml`) runs check, test, build and a
  `wrangler deploy --dry-run` on pushes and PRs.
- Changes go in PRs; visible ones with screenshots:
  `scripts/pr-shots.sh --pr <shot-name>...` uploads them to the orphan
  `pr-shots` branch and adds the Markdown to the branch's PR.

## Deploy

Cloudflare Worker `whenever` (never rename it: the custom domains are bound
to it), live since 2026-11-01. Workers Builds deploys on push to `main`.
Workers Builds ignores the `build` field in `wrangler.jsonc`: its Build
command must be `npm run build` (without it the deploy fails, as `dist/`
doesn't exist). Branch builds are not enabled, so branches only get CI.
If they are turned on, they run `wrangler preview`, which needs the
`previews` block in `wrangler.jsonc`: keep giving any new binding a
Preview-safe copy there. Rate-limit namespaces are account-wide:
`3001`/`3003` production, `3002`/`3004` previews (1001 is scoreboard,
2001/2002 scorepad). Secrets, set by the owner in the dashboard (type
Secret, so deploys keep them): `SMTP_USER` (`whenever@apphub.casa`) and
`SMTP_PASS` (its Forward Email SMTP password); without them asking for a
code answers 503. Workers Logs is on for console output only (invocation
logs off). Agent sessions
can't deploy (Cloudflare credentials there are read-only). Free plan:
SQLite-backed Durable Objects only, which this uses.
